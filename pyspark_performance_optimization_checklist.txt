1. CORE SPARK ARCHITECTURE FUNDamentals
================================================================================

[ ] Understand Spark Application Architecture
    - Driver program coordinates execution
    - Executor processes run tasks
    - Cluster manager (YARN, Mesos, Kubernetes, Standalone)
    - Task = unit of work on a partition
    - Stage = set of tasks that can be executed in parallel
    - Job = set of stages triggered by an action

[ ] Understand RDD vs DataFrame vs Dataset
    - RDD: Low-level, untyped, less optimized
    - DataFrame: Typed with schema, Catalyst optimizer
    - Dataset: Type-safe DataFrame (Scala/Java only)
    - Prefer DataFrames over RDDs for performance

[ ] Understand Lazy Evaluation
    - Transformations are lazy (map, filter, groupBy)
    - Actions trigger execution (collect, count, write)
    - DAG (Directed Acyclic Graph) built from transformations
    - Catalyst optimizer optimizes DAG before execution

[ ] Understand Lineage and Fault Tolerance
    - Lineage tracks transformation history
    - RDDs can be recomputed on failure
    - Checkpointing breaks lineage for long chains
    - Trade-off between recomputation and storage

[ ] Understand Execution Model
    - Narrow dependencies: data on same partition (map, filter)
    - Wide dependencies: require shuffle (groupByKey, reduceByKey)
    - Pipelining: narrow dependencies can be pipelined
    - Stage boundaries at wide dependencies

2. DATA PARTITIONING STRATEGIES
================================================================================

[ ] Understand Partitioning Basics
    - Partition = chunk of data processed by one task
    - Too few partitions: underutilized cluster, OOM
    - Too many partitions: overhead, small files problem
    - Target: 128MB-256MB per partition (HDFS block size)

[ ] Default Partitioning
    - Default partitions: spark.default.parallelism (RDDs)
    - Default partitions: spark.sql.shuffle.partitions (DataFrames, default 200)
    - Adjust based on data size and cluster resources

[ ] Repartition vs Coalesce
    - repartition(num): full shuffle, increases or decreases partitions
    - coalesce(num): no shuffle, only decreases partitions
    - Use coalesce when reducing partitions after filtering
    - Use repartition when need even distribution

[ ] Partitioning Strategies
    - Hash partitioning: default for most operations
    - Range partitioning: for ordered data
    - Custom partitioners: for specific distribution needs
    - Partition by column for joins/aggregations

[ ] Bucketing
    - Pre-shuffle data for frequent joins
    - df.write.bucketBy(numBuckets, "col").saveAsTable()
    - Reduces shuffle for subsequent joins
    - Works best for equality joins on bucketed columns

[ ] Partition Pruning
    - Partition data by frequently filtered columns
    - df.write.partitionBy("year", "month").parquet()
    - Spark reads only relevant partitions
    - Avoid too many small partitions (1000s of folders)

[ ] Salting for Skewed Data
    - Add random salt to keys for skewed joins
    - Explode skewed key into multiple keys
    - Join on salted key, then aggregate results
    - Reduces stragglers from data skew

[ ] Dynamic Partition Pruning
    - Spark 3.0+ feature
    - Prune partitions based on join conditions
    - Enabled by spark.sql.optimizer.dynamicPartitionPruning
    - Especially useful for star schema queries

3. MEMORY MANAGEMENT AND TUNING
================================================================================

[ ] Understand Spark Memory Model
    - On-heap memory: managed by JVM
    - Off-heap memory: managed by Spark (Tungsten)
    - Execution memory: shuffles, joins, sorts
    - Storage memory: caching/broadcasting
    - User memory: user data structures, UDFs

[ ] Memory Configuration
    - spark.executor.memory: total memory per executor
    - spark.memory.fraction: fraction for execution+storage (default 0.6)
    - spark.memory.storageFraction: fraction of execution+storage for storage (default 0.5)
    - spark.executor.memoryOverhead: off-heap memory for system overhead

[ ] Memory Tuning Guidelines
    - Leave 20-30% for OS and overhead
    - spark.memory.fraction: increase if OOM on shuffles
    - spark.memory.storageFraction: decrease if caching causes OOM
    - Monitor GC logs to tune

[ ] Garbage Collection Tuning
    - Use G1GC for large heaps (>4GB)
    - -XX:+UseG1GC -XX:MaxGCPauseMillis=200
    - Monitor GC time in Spark UI
    - Target: <10% of task time in GC

[ ] Off-Heap Memory
    - spark.memory.offHeap.enabled: enable off-heap
    - spark.memory.offHeap.size: off-heap memory size
    - Reduces JVM GC pressure
    - Used by Tungsten for binary format

[ ] Tungsten Memory Management
    - Binary in-memory format
    - Cache-aware computation
    - No Java object overhead
    - Enabled by default in Spark 2.0+

[ ] Spill to Disk
    - When memory insufficient, data spills to disk
    - spark.shuffle.spill: enable/disable spilling
    - spark.shuffle.spill.numElementsForceSpillThreshold
    - Monitor spill metrics in Spark UI

[ ] Memory Profiling
    - Use Spark UI Storage and Executors tabs
    - Check "Disk Spilled" and "Memory Spilled" metrics
    - Use -XX:+PrintGCDetails for GC analysis
    - Profile with Java Flight Recorder

4. SHUFFLE OPTIMIZATION
================================================================================

[ ] Understand Shuffle Operations
    - Wide dependencies trigger shuffle
    - Expensive: disk I/O, network I/O, serialization
    - Common shuffle ops: groupByKey, reduceByKey, join, distinct, reorder
    - Minimize shuffles in job logic

[ ] Reduce Shuffle Operations
    - Use reduceByKey over groupByKey (map-side combine)
    - Use aggregateByKey for complex aggregations
    - Filter before shuffle to reduce data volume
    - Combine multiple shuffles into one

[ ] Shuffle File Handling
    - spark.shuffle.file.buffer: buffer size for shuffle writes (default 32KB)
    - spark.shuffle.io.maxRetries: max retries for fetch failures
    - spark.shuffle.io.retryWait: wait between retries
    - spark.shuffle.service.enabled: enable external shuffle service

[ ] Shuffle Consolidation
    - spark.shuffle.consolidateFiles: consolidate shuffle files
    - Reduces number of open files
    - Important for large number of partitions
    - Enabled by default in Spark 1.6+

[ ] Shuffle Sort vs Hash
    - spark.shuffle.sort.bypassMergeThreshold: use hash shuffle for small reduces
    - Sort shuffle: default, better for large data
    - Tungsten-sort: optimized for primitive types
    - Auto-selected by Spark

[ ] Broadcast Hash Join
    - For small table joining large table
    - spark.sql.autoBroadcastJoinThreshold: max size for broadcast (default 10MB)
    - Set to -1 to disable, or higher to enable
    - Eliminates shuffle for small dimension tables

[ ] Shuffle Partition Count
    - spark.sql.shuffle.partitions: default 200
    - Too high: task overhead, small files
    - Too low: OOM, long tasks
    - Formula: total_data_size / target_partition_size (128MB)

[ ] Shuffle Read/Write Optimization
    - spark.sql.shuffle.partitions: adjust based on data
    - spark.shuffle.compress: compress shuffle data (default true)
    - spark.shuffle.spill.compress: compress spill data (default true)
    - Use LZ4 or ZSTD for faster compression

[ ] External Shuffle Service
    - spark.shuffle.service.enabled: enable external shuffle service
    - Allows executors to be removed without losing shuffle files
    - Required for dynamic allocation
    - Improves cluster utilization

5. CATALYST OPTIMIZER AND QUERY PLANNING
================================================================================

[ ] Understand Catalyst Optimizer
    - Rule-based optimization
    - Cost-based optimization (CBO)
    - Logical plan → Optimized logical plan → Physical plan
    - Uses statistics for cost estimation

[ ] Query Plan Analysis
    - df.explain(): view physical plan
    - df.explain(extended=True): view logical and physical plans
    - Look for: number of stages, join strategies, operations pushed down
    - Identify bottlenecks in plan

[ ] Predicate Pushdown
    - Filters pushed to data source
    - Reduces data read from storage
    - Works with Parquet, ORC, JDBC
    - Check plan for "PushedFilters"

[ ] Column Pruning
    - Only read required columns
    - Reduces I/O and memory
    - Automatic for DataFrames
    - Select only needed columns

[ ] Constant Folding
    - Compute constant expressions at compile time
    - Reduces runtime computation
    - Example: WHERE col > 10 + 5 → WHERE col > 15

[ ] Operator Reordering
    - Catalyst reorders operations for efficiency
    - Filters pushed before joins
    - Projections pushed after joins
    - Check plan for optimal order

[ ] Join Reordering
    - Star schema detection
    - Reorders joins based on size
    - Broadcast joins for small tables
    - Sort-merge joins for large tables

[ ] Cost-Based Optimization (CBO)
    - spark.sql.cbo.enabled: enable CBO
    - spark.sql.statistics.histogram.enabled: enable histograms
    - ANALYZE TABLE COMPUTE STATISTICS: collect table stats
    - ANALYZE TABLE COMPUTE STATISTICS FOR COLUMNS: collect column stats

[ ] Adaptive Query Execution (AQE)
    - Spark 3.0+ feature
    - Optimizes at runtime based on statistics
    - Features: dynamic coalescing, skew join handling
    - spark.sql.adaptive.enabled: enable AQE

[ ] Subquery Optimization
    - Scalar subqueries
    - EXISTS/IN subqueries
    - Correlated subqueries
    - Rewritten to joins when possible

6. DATAFRAME/DATASET API BEST PRACTICES
================================================================================

[ ] Use DataFrame API over RDD
    - Catalyst optimizer optimizations
    - Tungsten execution engine
    - Better memory management
    - 10-100x faster than RDDs

[ ] Use Built-in Functions
    - pyspark.sql.functions over UDFs
    - Vectorized operations
    - Catalyst optimizations
    - Example: F.col, F.sum, F.when

[ ] Avoid collect() on Large Data
    - collect() brings all data to driver
    - Can cause OOM on driver
    - Use take(), head(), show() for sampling
    - Use write() for saving results

[ ] Use SQL for Complex Queries
    - df.createOrReplaceTempView("table")
    - spark.sql("SELECT ...")
    - Often more readable for complex logic
    - Same optimizations as DataFrame API

[ ] Chain Operations
    - Chain transformations: df.filter().groupBy().agg()
    - Avoid intermediate variables
    - Allows Catalyst to optimize entire pipeline
    - More readable

[ ] Select Columns Explicitly
    - df.select("col1", "col2") over df["col1"]
    - Avoid df.select("*") when not needed
    - Reduces data movement
    - Enables column pruning

[ ] Use withColumn for Multiple Transformations
    - df.withColumn("new_col", expr)
    - Chain multiple withColumn calls
    - More efficient than creating new DataFrames

[ ] Avoid UDFs When Possible
    - Use built-in functions first
    - Use pandas_udf (vectorized UDF) if needed
    - Regular UDFs are slow (serialization)
    - Consider SQL expressions

[ ] Use Typed Operations
    - Use filter() with Column expressions
    - Avoid Python lambda functions
    - Example: df.filter(F.col("age") > 25)
    - Better than df.filter(lambda x: x.age > 25)

[ ] Handle Null Values Properly
    - Use F.isnull(), F.isnotnull()
    - Use F.coalesce() for default values
    - Use F.na.fill() for filling
    - Use F.na.drop() for removing

[ ] Use Window Functions Efficiently
    - from pyspark.sql.window import Window
    - Window.spec.orderBy().partitionBy()
    - Avoid multiple window operations
    - Cache before complex window operations

7. UDF OPTIMIZATION
================================================================================

[ ] Understand UDF Performance Impact
    - Regular UDFs: row-by-row processing
    - Serialization/deserialization overhead
    - No Catalyst optimization
    - 10-100x slower than built-in functions

[ ] Use Pandas UDFs (Vectorized UDFs)
    - pandas_udf: process batches as pandas Series
    - Arrow serialization: faster than pickle
    - spark.sql.execution.arrow.pyspark.enabled: enable Arrow
    - 10-100x faster than regular UDFs

[ ] Pandas UDF Types
    - Scalar pandas_udf: input/output scalar
    - Grouped Map pandas_udf: groupBy().apply()
    - Grouped Aggregate pandas_udf: custom aggregations
    - Window pandas_udf: window operations

[ ] Pandas UDF Best Practices
    - Use vectorized pandas operations
    - Avoid row-by-row iteration
    - Use pandas/numpy built-in functions
    - Minimize data transfer between Python and JVM

[ ] Regular UDF Optimization
    - Cache results if reused
    - Keep UDF logic simple
    - Avoid heavy computation in UDF
    - Use deterministic UDFs for caching

[ ] UDF Serialization
    - spark.sql.execution.arrow.pyspark.enabled: enable Arrow
    - spark.sql.execution.arrow.maxRecordsPerBatch: batch size
    - Larger batches = better performance, more memory
    - Tune based on data size

[ ] UDF Registration
    - spark.udf.register(): register for SQL
    - Use @udf decorator for DataFrame API
    - Specify return type explicitly
    - Example: @udf("double")

[ ] Avoid Python UDFs in Joins
    - UDFs in join conditions disable optimizations
    - Move UDFs before/after joins
    - Use built-in functions in join conditions
    - Consider materializing UDF results

[ ] Monitor UDF Performance
    - Check task duration in Spark UI
    - Compare with built-in function performance
    - Profile with Python profilers
    - Consider rewriting in Scala for critical paths

8. CACHING AND PERSISTENCE STRATEGIES
================================================================================

[ ] Understand Caching Levels
    - MEMORY_ONLY: store in memory, deserialized
    - MEMORY_ONLY_SER: store in memory, serialized
    - MEMORY_AND_DISK: memory + disk overflow
    - MEMORY_AND_DISK_SER: serialized memory + disk
    - DISK_ONLY: disk only
    - OFF_HEAP: off-heap memory

[ ] When to Cache
    - Data reused multiple times
    - Expensive computations
    - Iterative algorithms (MLlib)
    - Small-to-medium datasets

[ ] When NOT to Cache
    - Large datasets that don't fit in memory
    - Data used only once
    - Simple transformations
    - When shuffle is cheap

[ ] Cache Best Practices
    - Cache after expensive transformations
    - Unpersist when no longer needed: df.unpersist()
    - Use appropriate storage level
    - Monitor cache usage in Spark UI

[ ] Storage Level Selection
    - MEMORY_ONLY: default, fast, may lose data if OOM
    - MEMORY_AND_DISK: safer, slower on spill
    - MEMORY_ONLY_SER: more memory efficient, CPU overhead
    - DISK_ONLY: for very large data, slow

[ ] Cache vs Persist
    - cache() = persist(StorageLevel.MEMORY_ONLY)
    - persist() allows custom storage level
    - Use persist() for more control
    - Use cache() for simple cases

[ ] Broadcast Variables
    - Broadcast read-only data to all executors
    - sc.broadcast(variable)
    - Eliminates shipping data with each task
    - Use for lookup tables, config

[ ] Accumulators
    - Accumulate values across tasks
    - sc.accumulator(initial_value)
    - For counters, sums
    - Only driver can read value

[ ] Cache Monitoring
    - Spark UI Storage tab
    - Check fraction cached
    - Monitor memory usage
    - Remove unused caches

[ ] Cache Invalidation
    - Cache is lazy: computed on first action
    - Recomputed if lineage changes
    - Use checkpoint() to break lineage
    - Unpersist to free memory

9. BROADCAST VARIABLES AND ACCUMULATORS
================================================================================

[ ] Broadcast Variables
    - sc.broadcast(large_data)
    - Sent to each executor once
    - Efficient for shared read-only data
    - Reduces network overhead

[ ] When to Use Broadcast
    - Lookup tables
    - Configuration data
    - Small reference data
    - Machine learning models

[ ] Broadcast Best Practices
    - Broadcast data < 100MB typically
    - Use unpersist() when done
    - Avoid broadcasting mutable data
    - Monitor broadcast size in Spark UI

[ ] Broadcast Join
    - Automatic for small tables
    - spark.sql.autoBroadcastJoinThreshold
    - Manually broadcast: broadcast(df)
    - Eliminates shuffle for small table

[ ] Accumulators
    - sc.accumulator(0) for counters
    - sc.accumulator(0.0) for sums
    - Only driver can read value
    - Tasks can only add to value

[ ] Accumulator Types
    - LongAccumulator: integer values
    - DoubleAccumulator: floating point
    - CollectionAccumulator: collect values
    - Custom accumulators

[ ] Accumulator Best Practices
    - Use for metrics, debugging
    - Not for critical business logic
    - May be counted multiple times on retries
    - Reset value between actions

[ ] Broadcast vs Accumulator
    - Broadcast: send data to executors
    - Accumulator: collect data from executors
    - Broadcast for read-only sharing
    - Accumulator for aggregation

10. JOB SCHEDULING AND RESOURCE ALLOCATION
================================================================================

[ ] Cluster Resource Allocation
    - --num-executors: number of executors
    - --executor-cores: cores per executor
    - --executor-memory: memory per executor
    - --driver-memory: driver memory

[ ] Executor Sizing Guidelines
    - Cores per executor: 5-6 (leave 1 for OS/Hadoop)
    - Memory per executor: 30-60GB (avoid >64GB)
    - More executors with smaller memory is often better
    - Consider YARN container overhead

[ ] Dynamic Allocation
    - spark.dynamicAllocation.enabled: enable dynamic allocation
    - spark.dynamicAllocation.minExecutors: minimum executors
    - spark.dynamicAllocation.maxExecutors: maximum executors
    - spark.dynamicAllocation.initialExecutors: starting executors

[ ] Dynamic Allocation Benefits
    - Scale up during peak load
    - Scale down during idle periods
    - Better cluster utilization
    - Cost savings in cloud

[ ] Dynamic Allocation Requirements
    - External shuffle service required
    - spark.shuffle.service.enabled: true
    - Proper timeout configuration
    - Monitoring for executor churn

[ ] Fair Scheduler
    - spark.scheduler.mode: FAIR
    - Multiple pools with different weights
    - Prevents long jobs from starving short jobs
    - Configure pools in spark-defaults.conf

[ ] Speculative Execution
    - spark.speculation: enable speculative execution
    - spark.speculation.multiplier: slow task threshold
    - spark.speculation.interval: check interval
    - Retries slow tasks on other executors

[ ] Speculative Execution Considerations
    - Can cause duplicate work
    - Not safe for non-idempotent operations
    - Useful for stragglers
    - Monitor for wasted resources

[ ] Task Scheduling
    - spark.task.maxFailures: max task failures
    - spark.task.resource.gpu.amount: GPU allocation
    - spark.task.resource.gpu.discoveryScript: GPU discovery
    - Locality: NODE_LOCAL, RACK_LOCAL, ANY

[ ] Backpressure
    - spark.streaming.backpressure.enabled: enable backpressure
    - spark.streaming.backpressure.initialRate: initial rate
    - Adjusts ingestion rate based on processing time
    - Prevents overload

12. COMMON ANTI-PATTERNS TO AVOID
================================================================================

[ ] Anti-Pattern: Using RDDs When DataFrames Suffice
    - Problem: Miss out on Catalyst optimizations
    - Solution: Use DataFrame/Dataset API
    - Exception: Custom data types, low-level control

[ ] Anti-Pattern: collect() on Large Datasets
    - Problem: OOM on driver
    - Solution: Use take(), head(), or write to storage
    - Use count() for counts, not collect().count()

[ ] Anti-Pattern: Too Many Small Files
    - Problem: NameNode pressure, slow reads
    - Solution: coalesce() before write, proper partitioning
    - Target: 128MB+ per file

[ ] Anti-Pattern: groupByKey Instead of reduceByKey
    - Problem: Excessive shuffle, OOM
    - Solution: Use reduceByKey or aggregateByKey
    - Allows map-side combine

[ ] Anti-Pattern: Using UDFs Unnecessarily
    - Problem: Slow, no optimization
    - Solution: Use built-in functions or pandas_udf
    - Rewrite logic with SQL expressions

[ ] Anti-Pattern: Not Filtering Early
    - Problem: Processing unnecessary data
    - Solution: Filter as early as possible
    - Push filters to data source

[ ] Anti-Pattern: Repeatedly Reading Same Data
    - Problem: Unnecessary I/O
    - Solution: Cache frequently used data
    - Use persist() with appropriate level

[ ] Anti-Pattern: Creating Too Many Partitions
    - Problem: Task overhead, small files
    - Solution: Tune spark.sql.shuffle.partitions
    - Use coalesce() to reduce partitions

[ ] Anti-Pattern: Not Handling Skewed Data
    - Problem: Stragglers, long job times
    - Solution: Salting, broadcast joins, AQE
    - Monitor for skewed partitions

[ ] Anti-Pattern: Using SELECT *
    - Problem: Read unnecessary columns
    - Solution: Select only needed columns
    - Enables column pruning

[ ] Anti-Pattern: Ignoring Data Locality
    - Problem: Network overhead
    - Solution: Co-locate data with compute
    - Use appropriate storage formats

[ ] Anti-Pattern: Not Monitoring Performance
    - Problem: Miss optimization opportunities
    - Solution: Regular Spark UI review
    - Set up monitoring and alerting

[ ] Anti-Pattern: Hard-Coding Configuration
    - Problem: Not portable, hard to tune
    - Solution: Use config files, environment variables
    - Make configuration flexible

13. ADVANCED OPTIMIZATION TECHNIQUES
================================================================================

[ ] Whole-Stage Code Generation
    - Spark 2.0+ feature
    - Generates single Java function for query plan
    - Reduces virtual function calls
    - Enabled by default

[ ] Vectorized Query Execution
    - Process batches of rows
    - CPU cache friendly
    - Better for OLAP queries
    - spark.sql.inMemoryColumnarStorage.compressed

[ ] Codegen for Filter/Project
    - Generates optimized bytecode
    - Faster than interpreted execution
    - spark.sql.codegen.wholeStage: enable
    - spark.sql.codegen.factoryMode: codegen mode

[ ] Tungsten Project Optimizations
    - Binary in-memory format
    - Cache-aware algorithms
    - Off-heap memory management
    - Enabled by default

[ ] Adaptive Query Execution (AQE)
    - spark.sql.adaptive.enabled: enable AQE
    - spark.sql.adaptive.coalescePartitions.enabled: coalesce partitions
    - spark.sql.adaptive.skewJoin.enabled: handle skew
    - Runtime optimization based on statistics

[ ] Runtime Filter Optimization
    - Dynamic filtering on join probes
    - Reduces data scanned
    - spark.sql.runtimeFilter: enable
    - Especially useful for star joins

[ ] Join Hints
    - BROADCAST hint: force broadcast join
    - MERGE hint: force sort-merge join
    - SHUFFLE_HASH hint: force shuffle hash join
    - Example: df1.join(broadcast(df2), "key")

[ ] Bucketing and Sorting
    - Pre-bucket tables for frequent joins
    - Pre-sort for range queries
    - df.write.bucketBy().sortBy().saveAsTable()
    - Reduces shuffle for subsequent operations

[ ] Z-Ordering (Delta Lake)
    - Cluster data by multiple columns
    - Improves data skipping
    - OPTIMIZE table ZORDER BY (col1, col2)
    - Reduces I/O for point queries

[ ] Data Skipping
    - Parquet/ORC statistics
    - Min/max values per file
    - Partition pruning
    - Column statistics

[ ] Predicate Pushdown to Data Sources
    - JDBC: WHERE clause pushed to database
    - Parquet/ORC: filter at file level
    - Check query plan for PushedFilters
    - Reduces data transfer

[ ] Columnar Storage Formats
    - Parquet: default, good compression
    - ORC: better for Hive, compression
    - Delta Lake: ACID transactions, time travel
    - Choose based on use case

[ ] Join Types
    - Inner join: default, matching rows only
    - Left outer: all left rows, matching right
    - Right outer: all right rows, matching left
    - Full outer: all rows from both
    - Left semi: left rows with match (exists)
    - Left anti: left rows without match (not exists)

[ ] Join Strategies
    - Broadcast hash join: small table broadcasted
    - Sort-merge join: both tables large
    - Shuffle hash join: one table fits in memory
    - Broadcast nested loop join: very small tables

[ ] Broadcast Join Configuration
    - spark.sql.autoBroadcastJoinThreshold: threshold (default 10MB)
    - Increase for larger dimension tables
    - Set to -1 to disable
    - Use broadcast hint: broadcast(df)

[ ] Sort-Merge Join
    - Default for large tables
    - Sorts both sides by join key
    - Merges sorted data
    - Requires shuffle

[ ] Shuffle Hash Join
    - One table small enough to hash
    - spark.sql.join.preferSortMergeJoin: prefer sort-merge
    - spark.sql.autoBroadcastJoinThreshold: threshold
    - Falls back to sort-merge if table too large

[ ] Join Optimization Tips
    - Filter before joining
    - Join on most selective columns
    - Use appropriate join type
    - Consider denormalization

[ ] Join Hints
    - BROADCAST hint: force broadcast join
    - MERGE hint: force sort-merge join
    - SHUFFLE_HASH hint: force shuffle hash join
    - Example: df1.join(broadcast(df2), "key")

[ ] Join Order
    - Catalyst reorders joins based on size
    - Star schema detection
    - Broadcast smallest tables first
    - Check query plan for join order

[ ] Join Conditions
    - Use equality conditions for optimization
    - Avoid complex expressions in join
    - Use deterministic conditions
    - Consider composite keys

[ ] Handling Nulls in Joins
    - Nulls don't match in joins
    - Use coalesce for null handling
    - Consider outer joins for nulls
    - Filter nulls before join if appropriate

[ ] Join Performance Monitoring

    - Look for broadcast success/failure
